## 1. 工程结构（三种使用者三种格式）

```
guardrail/
├─ schemas/rule.md          专家唯一模板（字段定义 + 校验规则）
├─ rules/PHYS-0001..0016.md 16 条规则，专家写 Markdown + front matter（唯一真源）
├─ build.py                 编译器：Markdown → compiled/rules.json
│                           + index/{by-trigger,by-stage,by-mechanism,all}.md
├─ compiled/rules.json      ★ 检查器唯一输入
├─ index/*.md               人读的索引（按触发方式 / 阶段 / 致错机制）
└─ check.py                 确定性检查器（纯 Python，无 LLM、无网络）
```

配套的数据采集端在 `/home/shark/胡思乱想/1/g4dump/`：

| 文件 | 作用 |
|---|---|
| `hook.cc` → `hook.so` | LD_PRELOAD 拦截库（v4）：记录写操作 + 检测状态漂移 + 打「列表交付完成」标记 |
| `audit.cc` → `audit` | 被审计的蒙卡程序，另出配置文件快照 JSON |
| `out/*.rec` | 结构化记录（写动作 / 漂移 / 标记） |
| `out/*.json` | 配置快照（物理列表 / 构造器 / 过程 / 模型 / EM 参数 / 强子参数） |

## 2. 三条设计纪律（本批次实际遵守的）

1. **护栏不是 LLM。** 求值全在 `check.py` 里做，是查表程序：同样输入必出同样输出、可单测、可复现。
2. **规则里的话是专家写死的。** `question` 字段由专家撰写，检查器原样输出，Agent 不得改写。
   → 结构上堵住「护栏和 Agent 共享盲区、替错误决定背书」这个头号风险。
3. **能查配置就查配置，查不到就问，绝不用文本匹配猜。** 本批 16 条**没有一条**读用户源码。

## 6. 本批次修掉的两个真缺陷（设计层面的教训）

### 6.1 PHYS-0002 误报：把"列表自己装构造器"当成"用户额外加的"

**现象**：`G4PhysListFactory` 造列表时会自己调 `RegisterPhysics` 装 8 个构造器，
拦截库全记下来，规则把它们全报成"额外装的"。FTFP_BERT 基准配置一次误报 8 条。

**修法**：加一个「物理列表交付完成」标记。
拦截 `G4PhysListFactory::GetReferencePhysList`（`libG4physicslists.so` 0x123b40，
非 virtual，可拦）与 `ReferencePhysList`，返回后置位并写 `MARK|kind=list_ready|list=<名>`。
此后每条记录带 `phase=build`（列表自带）或 `phase=user`（列表之外）。
PHYS-0002 只匹配 `phase=user`。

**实测**：FTFP_BERT 的 8 个构造器全部 `phase=build`（零误报）；
thermal 的第 9 个 `ThermalNeutrons` 是 `phase=user`（准确命中）。

**★ 这个标记只对 `RegisterPhysics` 有效。** `RegisterMe` / `AddDataSet` 全部发生在
`Initialize()` 阶段（构造器的 `ConstructProcess()` 那时才跑），标记早翻过去了。
所以 PHYS-0008 不能靠它，改用汇总。

**★ 诚实性缺口（已补）**：若用户**手写物理列表**（不经过 `G4PhysListFactory`），
就永远没有标记，PHYS-0002 会**静默不报**。检查器现在会在报告末尾打告警：
「这一条本次无法判定。注意：不是「没装」，是「没看见」。」——已实测验证。

### 6.2 PHYS-0005 语义写反：`expect` 是"健康值"，不是"要抓的值"

**现象**：原本写 `expect: true`，本意是"有缝隙就报"，实际 `expect` 的语义是
「这个值才是正常的」，于是**没缝隙时反而报**。基准配置一次误报 1217 条。

**根因**：`expect` 与另一套写法 `value_is`（值恰等）语义相反，容易混。

**修法**：改用 `value_is: true`（有缝隙就报），语义直白。

**同时改了判据本身**：原来查 `model_count >= 2` 是错的 ——
Geant4 里一个过程挂多个模型是**常态**，而且区间**允许重叠**（HP 系列故意让
`NeutronHPElastic` 覆盖 0–20 MeV、`hElasticCHIPS` 从 19.5 MeV 起，留 0.5 MeV 过渡）。
改为派生事实 `coverage_gap`：**按能量排序后，若后一个模型的下限 > 前一个模型的上限**，
才是真缝隙。改完 7 个配置**零触发、零误报**。

## 7. 顺带测出来的新事实（本机实测，可复现）

选不同物理列表会**静默改变电磁/原子弛豫建模**，名字里完全看不出来：

| 配置 | Fluo 荧光 | Auger 俄歇 | UseICRU90Data |
|---|---|---|---|
| FTFP_BERT | False | False | False |
| QGSP_BIC | False | False | False |
| FTFP_BERT_HP | **True** | **True** | False |
| QGSP_BERT_HP | **True** | **True** | False |
| Shielding | **True** | **True** | False |
| QGSP_BIC_HP | **True** | **True** | **True** |

- 换成 `_HP` 列表，**荧光和俄歇电子默认被打开**。
- `QGSP_BIC_HP` 还额外打开了 `UseICRU90Data`（ICRU 90 号报告数据），别的列表都没开。

这三列全是检查器从快照里直接读出来的，没有人参与判断。

**另一个值得写进论文的对比**：`Shielding` 列表名不含 `_HP`，PHYS-0001（靠名字 glob `*_HP`）
**抓不到**它；但 PHYS-0003（靠漂移）**抓到了**同一处真实改动。
→ 名字匹配会漏，漂移检测不会。这是"该用哪一种触发方式"的直接证据。

## 8. 局限（必须如实写进论文）

1. **只有 Geant4。** OpenMC / FLUKA 未做。
2. **只有 Serial。** MT 多线程模式未测（`GetTree()` / 命令历史有 thread-local 语义）。
3. **拦截点只覆盖强子侧。** 三个拦截点全挂 `G4HadronicProcess` 与
   `G4VModularPhysicsList`，**EM 过程的写操作完全没覆盖**（最大窟窿）。
   EM 那部分目前只能靠快照读参数（PHYS-0009/0010/0011/0012/0015 就是这么做的）。
4. **header-inline setter 拦不住**，只能靠"两次可拦操作之间状态对比"。
   若两次可拦操作之间被改了又改回来，看不见。
5. **`audit_final_sweep()` 需被审计程序显式调用**（`G4RunManager::Initialize()` 是 virtual，
   LD_PRELOAD 拦虚拟调用不可靠），非侵入性打了折扣。
6. **规则是 Geant4 专用**，换程序要重写。
7. **规则覆盖率、误报率的正式统计还没做**（本批是 7 个配置的定性验证，不是评测）。

## 9. 复现命令

```bash
cd /home/shark/胡思乱想/1/g4dump
g++ -shared -fPIC -O1 -std=c++17 hook.cc -o hook.so $(geant4-config --cflags) -ldl
g++ -O1 -std=c++17 audit.cc -o audit $(geant4-config --cflags) $(geant4-config --libs)

AUDIT_RECORDS=out/FTFP_BERT.rec LD_PRELOAD=./hook.so ./audit base FTFP_BERT out/FTFP_BERT.json
AUDIT_RECORDS=out/FTFP_BERT_HP.rec LD_PRELOAD=./hook.so ./audit base FTFP_BERT_HP out/FTFP_BERT_HP.json
AUDIT_RECORDS=out/FTFP_BERT_thermal.rec LD_PRELOAD=./hook.so ./audit thermal FTFP_BERT out/FTFP_BERT_thermal.json

cd ../guardrail
python3 build.py
python3 check.py --snapshot ../g4dump/out/FTFP_BERT_HP.json \
                 --records  ../g4dump/out/FTFP_BERT_HP.rec --task-type all
```

**踩坑记录**：`grep -c` 无匹配时退出码为 1，会静默断掉 `&&` 链导致编译根本没执行 —— 用 `;` 或分开执行。
`strings hook.so | grep -c 中文` 在 C locale 下恒为 0（`strings` 按 isprint 判定，中文非 ASCII），
验证编译产物要用 ASCII 串（如 `MARK|kind=list_ready`）。
