# 链条 → 参数：完备性检验

**做法**：把 Geant4 11.2.2 里**所有可设置项**逐条塞进第 3 节的 18 问。
塞得进去 → 框架覆盖得住；塞不进去 → 要么漏了一问，要么这参数跟物理无关。

数据来源：
- 命令树：`/tmp/g4cmd_clean.tsv`，实测 **421 条**（构造 RunManager + 物理列表 + GPS + ScoringManager 后遍历全部）
- C++ 接口：本机安装头文件 `/home/shark/geant4/11.2.2-install/include/Geant4`
- 映射脚本：`docs/theory/链条参数映射.py`

## 3 ★ 四个"程序里没槽位"的问

这才是检验的真正输出。

### R3 怎么加权 —— 命令树 0 条，C++ 侧也是散的

```
基类 G4VPrimitiveScorer 里 "Weighted" 出现次数：0
有 Weighted(G4bool flg = true) 的具体计分器：16 个
```

```
$H/G4PSTrackLength.hh:55:        inline void Weighted(G4bool flg = true) { weighted = flg; }
$H/G4PSPassageTrackLength.hh:55: inline void Weighted(G4bool flg = true) { weighted = flg; }
$H/G4PSCellFlux.hh:64:           inline void Weighted(G4bool flg = true) { weighted = flg; }
```

**加不加权，是每个计分器各自决定的，基类没有统一开关。**
更麻烦的是有的是 `weighted=false` 默认（`G4PSTrackLength`），
有的根本没有这个开关、永远乘权重（`G4PSVolumeFlux`）。

→ 用户想确认"我这个计分器加权了吗"，得**逐个去翻 52 个类的头文件**。

### W1 权重记账 —— 命令树 0 条

命令树里一条都没有。全在 C++ 侧（27 个类）。
默认参数实读：`G4WeightWindowAlgorithm.hh:57-59`

```cpp
G4WeightWindowAlgorithm(G4double upperLimitFactor = 5,
                        G4double survivalFactor = 3,
                        G4int maxNumberOfSplits = 5);
```

### S6 绝对强度 —— 命令树 1 条，而且是相对强度

```
唯一的：/gps/source/intensity
```
它是**多个源之间的相对比例**，不是"每秒多少个 / 多少 Bq"。真正的绝对强度程序里没有。

### R5 误差多大 —— 命令树 2 条，全是外围

```
/run/beamOn          ← 事件数
/run/printProgress   ← 进度打印
```

**没有任何一条命令跟统计误差有关。** 与之前核验（`G4StatDouble::rms()` 全树零调用、
`/score/` 只 dump 三个裸量）完全一致。

## 4 ★ 用户指出的第二类：程序没有，但项目必须有

用户原话：**「程序没有，但是在实际项目需要肯定有」**。

这句话把"决策点集合"和"程序可配置集合"**明确分开了**：

```
   项目必须交代的
   ┌──────────────────────────────────────┐
   │  程序有槽位        │  程序没槽位        │
   │  （能查/能配）      │  （只能问）        │
   ├────────────────────┼──────────────────┤
   │  S1..S5  T1..T6    │  S6 绝对强度       │
   │  R1 R2   W1        │  R4 归一化基准     │
   │                    │  R5 误差要求       │
   │                    │  R3 加权口径       │
   └────────────────────┴──────────────────┘
                 ↑ 枚举程序参数，这一半永远查不到
```

**这就是最早那个 idea 的内核**：「用户不知道该输入什么」——
用户不知道该输入，是因为**程序压根没给他输入的地方**。
程序不问，用户就以为不需要，于是这四个环节全部默认由 AI 悄悄定。

**这一条同时决定了护栏的形态**：
- 程序有槽位的 → 护栏**读配置**查
- 程序没槽位的 → 护栏**只能问**，而且要问得具体（"你要的是每源粒子还是每秒？"不是"归一化怎么设？"）

## 5 副产物：28% 的命令根本不是物理决策

命令树 421 条里，**118 条（28%）是计算控制**：宏语言（`/control/` 32 条）、
性能剖析（`/profiler/` 20 条）、打印重定向（`/control/cout/` 6 条）、
运行控制（`/run/` 大部分）、事件栈、单位表……

**这条对论文有用**：它说明"数程序有多少个可设置项"这个做法本身会**严重高估**
物理决策点的数量 —— 四分之一以上跟物理无关。

---

## 6 一处需要修的地方：可复现性

命令树 `/random/` 8 条（种子、状态存取、检查点）**落在 18 问之外**。

它跟 R5 是同一件事：**这个数能不能信、能不能复查**。

我建议**不新增第 19 问**，而是把 R5 从"误差多大"扩成
**「统计与可复现」**：事件数、收敛判据、统计误差定义、随机数种子、检查点。

理由：它们回答的是同一个问题——"这次计算的结果，凭什么可信"。

---

## 7 18 问的一个新属性：程序支持度

检验顺带给每一问标出了"程序给不给入口"。这在护栏里直接对应四种动作：

| 程序支持度 | 哪些问 | 护栏该做什么 |
|---|---|---|
| **有专门命令，可直接读** | S1–S5、T3、T5、R1、R2 | 读配置，报事实 |
| **有接口，但散落、无统一入口** | R3（16/52 个计分器各自有开关） | 逐个查，报"你这个到底加没加" |
| **只在 C++ 层，命令树没有** | T1、T2、T4、T6、W1 | 读源码/快照，命令层查不到 |
| **程序完全没有** | **S6、R4、R5** | **只能问** |

## 8 结论

1. **18 问站得住**：命令树 421 条 + C++ 层全部装得下，0 条落不进去。
   → 完整性问题从"我数全了吗"变成"框架装得下吗"，前者无解，后者可验证。

2. **有界的 18 问** 直接回答最早的批评"Agent 能做几百上千个物理决定，无界"。

3. **新增一类决策点**：程序没槽位、项目必须有的（S6/R4/R5/R3）。
   这解释了最初那个 idea 的内核——用户不知道该输入什么，
   因为程序没给他输入的地方。

4. **28% 的命令不是物理决策**：说明"数开关"会高估决策点数量。

## 遗留

1. 62 条兜底归类的命令没逐条细看。
2. 只做了 Geant4。OpenMC / FLUKA 的对应关系没做——但框架不变，只换实例。
3. 只做了"可设置项"。**模型内部的物理选择**（比如某个强子模型的能量下限）
   不在可设置项里，是程序写死的默认值 —— 这类已由前置的漂移检测覆盖，
   但**在本检验里没有对应位置**，需要单列。
